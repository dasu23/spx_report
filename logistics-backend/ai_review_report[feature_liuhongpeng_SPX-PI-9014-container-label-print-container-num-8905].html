    MAJORL49并发安全⚠ 行号未验证
    问题

    ContainerNumAllocator.allocate(ContainerForm template, int qty) 在新事务里先调用 findLatestSeq(containerPrefix) 读当前最大序号，再基于该值计算 firstSeq。

    这是一段典型的 check-then-act 并发分配逻辑，当前实现完全依赖唯一索引冲突后抛 DataIntegrityViolationException 再由上层重试，没有在数据库层做行级锁、序列表或原子自增保护。

    后果

    当同一个 containerPrefix 被并发打印时，多个请求会反复撞到同一批序号并整批回滚；

    在高并发或批量打印场景下，这会把正常业务流量放大成持续重试，导致 POST /batch-print 与 POST /batch-print-v2 出现明显失败率上升，形成可被触发的拒绝服务风险。

    怎么改

    把 ContainerNumAllocator.allocate 改成数据库原子分配方案，不要用“先查 max(seq) 再批量插入”作为主路径。

    可选修复包括：为 containerPrefix 建独立计数表并使用 select ... for update / 原子 update ... set seq = seq + ? 返回区间，或使用数据库 sequence/号段表统一发号；

    这样上层无需依赖异常重试来保证正确性。

    怎么验

    准备两个并发请求同时调用 POST /batch-print-v2，请求体中都包含相同 sortId 与相同 sortDate 的一行数据，使它们生成相同 containerPrefix。

    持续压测 50~100 次，观察是否频繁出现 Printing is busy, please retry.，并验证修复后同样并发下不再依赖唯一索引冲突重试。
