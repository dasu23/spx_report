    pos-service/src/main/java/com/miq/posservice/service/container/ContainerNumAllocator.java1 Major1 个问题
    MAJORL49并发安全⚠ 行号未验证
    问题

    ContainerNumAllocator.allocate(ContainerForm template, int qty) 在新事务里先调用 findLatestSeq(containerPrefix) 读取当前最大序号，再基于 firstSeq = findLatestSeq(containerPrefix) + 1 批量构造并 saveAll(records)。

    这属于典型的先查后写分配号段，当前实现把并发冲突完全留给唯一索引异常处理，但没有数据库级锁、序列表或单条原子自增来保证号段分配原子性。

    后果

    并发打印同一 containerPrefix 时，多个请求会反复撞到同一批序号并触发 DataIntegrityViolationException 回滚；

    在高并发下会形成热点竞争，导致 POST /batch-print 频繁返回 Printing is busy, please retry.，造成可被正常业务流触发的拒绝服务式可用性风险。

    怎么改

    把 ContainerNumAllocator.allocate 改为数据库原子分配号段，而不是 findLatestSeq 后再 saveAll。

    可选方案包括：为 containerPrefix 建独立计数表并使用 SELECT ... FOR UPDATE/乐观锁更新当前序号，或使用数据库 sequence/自增表一次性预留 qty 个序号，再按预留结果插入 ContainerNumRecord。

    这样可以从根源消除并发重试风暴。

    怎么验

    并发发起多次针对同一 sortId、同一 sortDate 的 POST /batch-print 请求，每次 printQty 取 50，观察是否出现大量 Printing is busy, please retry.；
