    问题

    新增的 '/cdn-pod/' 代理把 req.path 中用户可控的首段直接当作 router 的目标主机名，return https://${host}/; 没有任何白名单、格式校验或固定域名约束，同时 pathRewrite 还会剥掉前缀把后续路径原样转发。

    这样开发/测试环境中的浏览器请求 /cdn-pod/<任意host>/<path> 时，会被前端开发代理主动发往任意外部 HTTPS 主机。

    后果

    只要有人能诱导开发或测试环境访问特制的 /cdn-pod/ URL，就可以借当前前端代理对内网地址、云元数据地址或未公开外部服务发起请求，形成典型的 SSRF/开放代理 风险；

    若目标服务基于来源网络放行，还可能扩大到内网探测或敏感资源读取。

    怎么改

    把 router 改成只允许受信任的 POD 图片域名白名单，禁止直接使用 req.path 中的任意 host 作为 target；

  }

    src/pages/reverse-logistics/batch/ModalUploadReverseBatchPod.tsx1 Major1 个问题
    MAJORL149-155前端安全
    问题

    handleDownload 直接把服务端返回的 pod.url 赋给动态创建的 <a> 元素的 href，且没有校验协议或来源域名。

    只要 ReverseBatchPod.url 被污染为 javascript:、data: 或其他非预期协议，这段代码就会在用户点击下载图标时执行不受信任的 URL。

    后果

    一旦后端数据、存储元数据或中间链路把恶意 URL 写入 pod.url，拥有 reverse:batch:pod:list 的用户点击下载按钮就可能触发前端脚本执行或被跳转到恶意站点，形成存储型前端注入/钓鱼入口。

    怎么改

    在 handleDownload 中先对白名单协议和可信 host 做校验，只允许 https:（必要时再允许 http:）且域名属于预期的对象存储/CDN；

    校验失败时直接 message.error 并拒绝创建链接。示例：

    const handleDownload = (pod: ReverseBatchPod) => {
  try {
    const parsed = new URL(pod.url, window.location.origin);
    const allowedProtocols = ['https:'];
    const allowedHosts = ['blob.example.com'];
    if (!allowedProtocols.includes(parsed.protocol) || !allowedHosts.includes(parsed.host)) {
      message.error(intl.formatMessage({ id: 'pages.action.download.fail' }));
      return;
    }
    const link = document.createElement('a');
    link.href = parsed.toString();
    link.download = pod.fileName;
    link.target = '_blank';
    link.rel = 'noopener noreferrer';
    document.body.appendChild(link);
    link.click();
    document.body.removeChild(link);
  } catch {
    message.error(intl.formatMessage({ id: 'pages.action.download.fail' }));
  }
};
