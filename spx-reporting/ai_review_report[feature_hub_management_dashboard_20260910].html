    MAJORL441-446权限与访问控制
    问题

    hmd_detail_submit 新增把客户数据范围直接序列化到异步任务参数里：scope_org_ids = (None if scope.customer_unrestricted else sorted(scope.org_ids))，随后写入 consumer_params。

    这条链路把请求线程上解析出的授权边界降级成了一个可转发的数据字段，但本分片 diff 没有展示与之配套的签名、防篡改校验或消费者侧强制重算逻辑；

    注释还明确说明“Forwarded rather than recomputed on the consumer”。

    这意味着导出任务的最终权限边界取决于队列/持久化参数是否可信，而不是取决于消费者重新基于当前请求身份做授权判定。

    后果

    一旦 SaveReportRequest 后续链路允许修改 report_params、重放旧任务，或消费者对 scope_org_ids 直接信任，攻击者就可能通过伪造 scope_org_ids 扩大 org_id 可见范围，导致异步导出结果与当前用户真实 FTAC customer scope 不一致，形成跨客户数据越权导出。

    由于这里是离线文件导出，越权结果通常更难被前端即时发现。

    怎么改

    把 scope_org_ids 从“可信授权结果”改成“仅作提示参数”：在消费者执行查询前，基于任务提交者身份重新调用与 get_request_data_scope() 等价的服务端授权逻辑，重新计算 org_id 范围，并忽略消息体里传入的 scope_org_ids。

    如果当前架构必须透传范围，至少要对 consumer_params 做服务端签名并在消费者侧验签，验签失败直接拒绝执行。

    怎么验

    准备一个 customer-restricted 用户提交导出任务，先正常抓取一次入队参数；

    然后在任务落库或消息转发链路中把 scope_org_ids 改成包含该用户未授权的 org_id 列表，再触发消费者执行。验证消费者是否仍会重新按提交者身份收敛到原始授权范围；

    如果导出文件出现未授权 org_id 数据，则说明存在越权导出风险。

    MAJORL356-374权限与访问控制
    问题

    新增的 resolve_scope_org_ids(params: dict) 允许在 report_params 中同时兼容 scope_org_ids 和旧字段 customer_denied，并在缺少 scope_org_ids 时直接执行 return [] if bool(params.get("customer_denied")) else None。

    这里把旧模型里的布尔值 customer_denied=False 直接翻译成 None（无限制），但从本分片代码无法证明旧任务一定不存在客户维度允许列表；

    也就是说，只要旧任务没有写入 scope_org_ids，消费端就会把它当成“客户轴不受限”。

    后果

    对仍在队列中的旧任务，任何原本依赖 Portal 侧更细粒度客户范围控制、但只落库了 customer_denied=False 的请求，都会在消费端被放大为查看全部 org_id 数据。

    这属于典型的数据范围越权风险；由于本分片未包含提交任务的 HTTP 映射，外部入口路径无法从 diff 直接确认。

    怎么改

    收紧 resolve_scope_org_ids 的兼容策略：仅在能够从 report_params 明确恢复旧任务的客户范围时才继续执行；

    否则对缺少 scope_org_ids 且 customer_denied 为 False 的旧任务直接失败关闭，而不是返回 None。

    如果确有历史任务需要兼容，应在 report_params 中补写明确的 scope_org_ids 后再消费。

    怎么验

    构造一个仅包含 customer_denied=false、不包含 scope_org_ids 的历史 report_params，并让底层事实表存在多个不同 org_id 的数据。

    执行导出后，验证结果是否返回了所有 org_id 的记录；若是，则说明旧任务被放大为无限制访问。
