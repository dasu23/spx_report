    CRITICALL35-41权限与访问控制
    问题

    ApiIpWhitelistInterceptor.preHandle 在 apiKey 为空时直接 return true，且 rpsIpWhitelistConfig.allowedIpsOf(apiKey) 返回空列表时也直接 return true。

    这意味着 ConfigInterceptor.addInterceptors 新挂载到 /label/create-label、/tracking/、/pickup/、/admin/subscriber/queryUser 等路径上的 apiIpWhitelistInterceptor 实际是“仅当请求头里主动带了已配置 apiKey 才校验 IP”，未带 ConstantParameter.API_KEY 或带了未配置的 apiKey 都会被放行，而不是默认拒绝。

    如果这些路径原本期望通过 IP 白名单限制来源，攻击者只需不传 ConstantParameter.API_KEY，就可以绕过新增的来源限制直接访问接口；

    把 ApiIpWhitelistInterceptor.preHandle 改为默认拒绝策略：对已接入 apiIpWhitelistInterceptor 的路径，缺少 ConstantParameter.API_KEY 或 rpsIpWhitelistConfig.allowedIpsOf(apiKey) 为空时都应直接拒绝；

    只有命中配置且 IpUtil.matchesAny(clientIp, allowedIps) 为真时才放行。

    若确实存在无需白名单的接口，应在 ConfigInterceptor.addInterceptors 中不要把这些路径加入 apiIpWhitelistInterceptor，而不是在拦截器里静默放行。

    问题
