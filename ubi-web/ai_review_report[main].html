    backend/server/src/main/java/com/ubi/server/common/interceptor/AuthInterceptor.java2 Major2 个问题
    MAJORL132-136异常处理
    问题

    resolveWorkbenchSession(HttpServletRequest request) 在调用 PlatformAuthenticator.authenticate(token) 时捕获了过宽的 RuntimeException，并直接 log.warn(...) 后 return null，把「平台 token 非法 / SDK 故障 / 平台撤销态校验异常」与「根本没有 Workbench 会话」混成同一种返回值。

    这样调用方会继续回落到本系统自签会话分支，无法区分这是正常的多认证源切换，还是一次本应被显式拒绝或告警升级的认证异常。

    后果

    当请求同时携带 Authorization 头和 Workbench Cookie，且 Authorization 头中的 token 可被 jwtUtils.parseToken(...) 接受时，攻击者或异常客户端可以通过构造一个触发 PlatformAuthenticator.authenticate(token) 抛出 RuntimeException 的 Workbench token，让平台侧的撤销、禁用或单点登出状态被静默降级为本地 JWT 登录态继续放行；

    同时运维侧也只能看到一条 warn 日志，难以及时发现认证链路异常。

    怎么改

    把 PlatformAuthenticator.authenticate(token) 的异常分成“明确的认证失败”和“基础设施异常”两类处理：认证失败可以按未通过处理，但基础设施异常不要回落到本系统自签会话，应直接抛出 BusinessException.unauthorized("Unauthorized") 或 5xx，让调用方感知认证链路异常。

    至少要避免对“请求已携带 Workbench token 但平台校验异常”的场景继续尝试另一套会话。

    怎么验

    构造一个请求，同时携带 Authorization: Bearer <有效本系统JWT> 和 Workbench Cookie；

    mock PlatformAuthenticator.authenticate(token) 抛出 RuntimeException。当前代码会继续使用本系统 JWT 放行。

    修复后应验证该请求被拒绝，且不会进入本系统自签会话回落分支。

    问题

    WebMvcConfig 新增了对 /sso/ 的统一放行，但当前 diff 里只给出了路径级别的豁免说明，没有同时展示对 SsoGateway、Workbench SDK 自动装配端点或对应 Controller/Filter 的方法级来源校验、状态参数校验或仅限框架内部回调的约束。也就是说，这次变更把整个 /sso/ 路径前缀从 authInterceptor 保护范围中移除了，但本分片无法证明该前缀下所有入口都应当匿名可达。

    +                        // Workbench SDK 自动装配的登录/登出/换票端点，它们都在用户尚未登录时被访问。
+                        // 漏放行的表现是「登录后回跳又被弹去平台」的死循环，而 302 到平台那一跳看起来完全正常。

    后果

    如果 Workbench SDK 在 /sso/** 下除了登录/登出/换票外还暴露了其他调试、回调或票据处理入口，匿名请求现在都可以直接命中这些端点；一旦其中任一端点缺少二次校验，就可能被外部调用者利用，造成登录流程被探测、票据处理被滥用，甚至形成未授权访问面扩大。

    怎么改

    把放行范围从 "/sso/**" 收缩为实际需要匿名访问的精确路径，并逐个在对应入口补充来源校验与失败处理测试；如果确实只能按前缀放行，至少在 AuthInterceptor 之外再增加对 state/回调来源/一次性票据的严格校验，并在代码注释中列明被覆盖的具体端点清单。

    怎么验

    在集成测试中枚举 Workbench SDK 实际注册到 /sso/ 下的全部 HTTP 入口：对登录回调所需端点验证匿名访问成功；对非登录必需端点验证匿名访问被拒绝或因缺少合法票据/状态参数失败，避免 "/sso/" 前缀放行后出现额外匿名可达接口。
