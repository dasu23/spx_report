    backend/server/src/main/java/com/ubi/server/common/auth/WorkbenchApiKeyOwnerChecker.java1 Major1 个问题
    MAJORL71-74异常处理
    问题

    WorkbenchApiKeyOwnerChecker.queryPlatform 在第二次调用 matchAccess(email, 0, platformUserId) 时，把 RuntimeException 直接吞掉并返回 false。

    这会把「平台检索接口因为网络抖动、鉴权失败、限流等异常而失败」与「该用户确实不具备 Permissions.ACCESS」混为同一种结果，违背了同文件前文 isActive 中“平台查询失败不缓存且拒绝，下次请求会重新向平台查询”的 fail-closed 设计。

    后果

    当 grantedUserClient.searchWithPermissions(email, 0, SEARCH_PAGE_SIZE) 因瞬时异常失败，而第一页基数实际是 0、第一次 page=1 只是未命中时，isActive 会把仍然有效的 API Key 持有人误判为不活跃并把 false 写入缓存 60 秒，导致合法请求被持续拒绝，形成可被外部平台波动触发的认证拒绝服务。

    怎么改

    修改 WorkbenchApiKeyOwnerChecker.queryPlatform，不要在第二次 matchAccess(email, 0, platformUserId) 的 catch (RuntimeException e) 中返回 false；

    应将异常继续抛出给 isActive，由 isActive 统一按“拒绝但不缓存”处理。可改成仅在能明确识别“页码 0 非法”这一特定异常时降级为 false，其他异常继续抛出。

    怎么验

    模拟 grantedUserClient.byUserId(platformUserId) 返回带邮箱的用户；

    第一次 searchWithPermissions(email, false, 1, SEARCH_PAGE_SIZE) 返回空列表，第二次 searchWithPermissions(email, false, 0, SEARCH_PAGE_SIZE) 抛出瞬时 RuntimeException。

    验证 isActive(ownerId) 返回 false 但不会把该结果写入 cache，随后下一次调用仍会重新访问平台，而不是命中缓存。

    return matchAccess(email, 0, platformUserId).orElse(false);
