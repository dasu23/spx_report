    MAJORL9-12安全风险
    问题

    新增的 docs/jenkins-deploy.md 直接给出了从仓库根 .env 读取 JENKINS_USER、JENKINS_PASSWORD 并拼接成 AUTH="$JENKINS_USER:$JENKINS_PASSWORD" 的操作方式，后续示例又反复把 -u "$AUTH" 直接传给 curl。

    这会把明文凭据放进 shell 变量，并极易进入 shell history、调试输出、进程参数列表或 CI 日志。

    后果

    开发者按文档执行时，Jenkins 凭据可能被同机其他用户通过进程列表读取，或在排障时被复制进聊天记录/日志，导致构建与部署权限泄露。由于该文档是操作说明，风险会被重复传播给所有使用者。

    怎么改

    把文档改为使用 curl --netrc-file、受限权限的临时凭据文件，或至少分别使用 JENKINS_USER 与 JENKINS_PASSWORD，避免把 user:password 合并成一个易泄露的命令行参数；

    同时补充“禁止开启 shell xtrace/禁止把命令输出贴到日志”的明确说明。

    怎么验

    按修订后的文档执行一次 Jenkins 调用，确认 ps 或等价进程查看方式中不会出现完整的 user:password；

    同时检查 shell history 与构建日志模板，确认不会记录明文 Jenkins 凭据。

    证据代码
    AUTH="$JENKINS_USER:$JENKINS_PASSWORD"

    问题

    export function getKafkaSyncLog(token: string, logId: number) {

    CRITICALL23安全风险
    问题

    新增配置 enableXsrfProtection = false，直接关闭了 Streamlit 服务端对跨站请求伪造的内建防护。

    该变更位于 frontend/.streamlit/config.toml 的 [server] 配置段，且注释明确说明是为了让 _stcore/upload_file 不再因多副本/非粘性负载均衡返回 400。

    后果

    只要用户浏览器里带着现有登录态 cookie 访问恶意站点，攻击者就可以诱导浏览器向同源反向代理后的 Streamlit 接口发起跨站请求；

    在文件上传、表单提交或其他有副作用的 Streamlit 交互场景下，这会把原本应由 XSRF token 阻断的请求放行，扩大为真实的跨站操作风险。

    怎么改

    恢复 enableXsrfProtection = true，并改为在反向代理或负载均衡层解决多副本场景下的 token/会话一致性问题，例如保证 _stcore/upload_file 请求命中同一会话实例，或统一共享会话状态；

    不要用全局关闭 XSRF 保护来规避 400。若确实存在上传链路兼容性问题，至少应仅对受控上传入口做定向豁免，而不是关闭整个 Streamlit 服务的 XSRF 防护。

    怎么验

    使用已登录浏览器打开第三方恶意页面，由该页面自动构造一个指向 Streamlit 有副作用接口（至少覆盖 _stcore/upload_file）的跨站 POST 请求；

    验证在 enableXsrfProtection = true 时请求被拒绝，而当前配置下请求会被服务端接受。

    证据代码

    一旦 DRS_APP_URL 被误配为 javascript:、data: 等危险 scheme，这段 unsafe_allow_html=True 会把它直接注入为可点击链接。

    怎么改

    在 resolve_drs_app_base_url 或 _same_tab_external_link 中对白名单协议做强校验，只允许 https://（必要时允许 http:// 的本地开发环境），不符合时直接返回空串并不渲染链接。

    可参考：

    from urllib.parse import urlparse

parsed = urlparse(explicit)
if parsed.scheme not in {"https"}:
    return ""

    同时保留 escape，但不要把协议校验寄希望于 HTML 转义。

    怎么验

    将 DRS_APP_URL 配置为 javascript:alert(1)，打开侧边栏并点击 Generate Route；修复前浏览器会尝试执行该 scheme，修复后菜单不应渲染或点击无效。
