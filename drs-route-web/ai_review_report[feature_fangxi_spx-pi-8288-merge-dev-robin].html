    MAJORL358-359安全风险
    问题

    get_pickup_route_auto_sync_config 新增的异常分支把 SQLAlchemyError、RuntimeError、OSError 的原始内容直接拼到 HTTPException(detail=detail) 返回给调用方，其中 detail = str(getattr(exc, "orig", None) or exc) 会优先暴露底层数据库驱动的 orig 异常文本。

    数据库异常文本通常会包含表名、列名、约束名、SQL 片段甚至连接侧错误细节。

    后果

    任何能访问 GET /auto-sync/pickup-route/config 的调用方都可以通过触发数据库或文件系统异常来枚举后端内部实现细节，降低后续针对数据库结构、部署路径和依赖组件的攻击成本；

    同时把原本的 500 改成 409 也会误导前端把基础设施故障当成业务冲突处理，掩盖真实告警。

    怎么改

    把 detail 改为固定的业务错误文案，并仅在服务端日志中记录 exc/exc.orig。

    例如保留 raise HTTPException(status_code=500, detail="获取配置失败")，同时用结构化日志记录异常堆栈；

    如果确实要区分冲突类错误，应只对白名单业务异常返回 409，不要把 SQLAlchemyError 和 OSError 的原文透传给客户端。

    怎么验

    构造一次数据库约束错误或连接错误，让 get_pickup_route_auto_sync_config 落入该分支；

    验证 HTTP 响应体不包含数据库表名、列名、约束名、SQL 关键字或文件路径，只返回固定业务文案，同时服务端日志仍能看到完整异常。

    backend/app/services/pudo_route_generate/vinted_route_kafka_consumer_loop.py1 Info1 个问题
    INFOL79数据一致性
    问题

    run_consumer_loop 在 finally 中无条件执行 consumer.commit()，即使 handle_raw_kafka_message 抛出了异常也会提交 offset。

    代码注释虽然声称失败已落日志后继续消费，但这里并没有根据处理结果区分“可安全提交”和“必须保留待重试”的失败类型。

    后果

    只要 handle_raw_kafka_message 在真正完成数据库写入、补偿记录或失败审计之前异常退出，这条 Kafka 消息的 offset 仍会被提交，重启后不会再被重新消费，形成不可恢复的消息丢失。

    攻击者或异常上游只需构造一条触发处理异常的消息，就可能让对应业务数据永久缺失。

    怎么改

    把 consumer.commit() 移到确认 handle_raw_kafka_message 已完成且失败状态已可靠持久化之后，再按结果决定是否提交；

    对于未能确认落库的异常，应保留 offset 不提交，让消息可被重新消费。

    怎么验

    构造一条会让 handle_raw_kafka_message 在进入处理后立刻抛异常、且未完成失败日志落库的消息；

    运行 run_consumer_loop 处理该消息后重启消费者，验证该 offset 不应已提交，消息应能再次被拉取。
