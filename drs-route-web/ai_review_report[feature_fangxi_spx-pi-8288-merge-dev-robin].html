    backend/app/api/v1/auth.py1 Major1 个问题
    🔒 安全/权限相关 · 1 项（点击展开）
    MAJORL162-164权限与访问控制
    问题

    _request_host 直接信任 request.headers.get("x-forwarded-host")，并把结果传给 _cookie_domain / resolve_auth_cookie_domain 用于决定 response.set_cookie(..., domain=...) 和 response.delete_cookie(..., domain=...)。

    这意味着 /api/v1/auth/browser-login、/api/v1/auth/browser-refresh、/api/v1/auth/browser-logout 的 cookie 作用域由请求头驱动，而不是由受信任的反向代理配置或服务端固定配置决定。

    后果

    只要后端可被直接访问，攻击者就能伪造 X-Forwarded-Host: anything.speedx.io 触发服务端下发 Domain=.speedx.io 的共享登录 cookie，扩大会话在整个父域下的可用范围；

    在多子域并存场景下，这会把原本应绑定当前 Host 的会话提升为跨子域可携带，增加会话被其他子域接收或滥用的风险。

    怎么改

    把 _request_host 改为只在明确受信任代理链下才读取 x-forwarded-host，否则仅使用 request.headers.get("host") 或直接使用 settings.AUTH_COOKIE_DOMAIN 固定值。

    至少应增加对来源代理的白名单校验，避免客户端直传头部影响 cookie 域名。

    def _request_host(request: Optional[Request]) -> str:
    if request is None:
        return ""
    return request.headers.get("host") or ""

    如果必须支持代理转发，应在可信代理中间件完成 host 规范化后再读取，而不是在业务代码里直接信任原始请求头。

    怎么验

    直接向 POST /api/v1/auth/browser-login 发送请求，并手工附带 X-Forwarded-Host: drs-v2-sit2.speedx.io 与一个非该域名的实际访问 Host；

    验证响应里的 Set-Cookie 是否被写成 Domain=.speedx.io。再用未带该伪造头的同一请求对比，确认客户端可控请求头是否改变了会话 cookie 的作用域。
