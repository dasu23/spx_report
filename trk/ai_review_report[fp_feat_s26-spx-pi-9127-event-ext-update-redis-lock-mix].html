    MAJORL29-31需求矛盾🔄 行号已纠正
    问题

    需求原文 Brief Summary 明确限定聚合逻辑适用于“non-closed-loop packages”，即非闭环包裹才需要继续吸收后续图片更新；

    但 UpdateEventExtCmd 的实现说明明确写了“不校验包裹闭环”，且方法体中也没有任何闭环状态判断或分支。代码行为因此覆盖到了需求未授权的闭环包裹场景。

    后果

    闭环包裹收到后续 POS 补图时，当前实现仍会更新 tb_event_ext 并可能重推工单，导致闭环后的轨迹扩展信息继续被改写，不符合需求限定的适用范围。

    怎么改

    在 UpdateEventExtCmd.updateExt 中补充闭环状态判断，仅对需求要求的 non-closed-loop packages 执行扩展信息更新与后续重推；闭环包裹应按需求约束拒绝或跳过。

    校验未闭环包裹会更新扩展信息，而已闭环包裹不会更新 tb_event_ext、不会新增 TRK_TO_TICKET_EVENT 任务。

    MAJORL29-31, 63-67需求矛盾
    问题

    需求原文在「Business Requirement Document → Complication」明确写的是“merges additional images into existing records for non-closed-loop packages”“ensures the final image set reflects all updates（e.g., combining images from 08:00 and 10:00 updates）”，即同一轨迹后续补传图片要与已有图片聚合；

    但 UpdateEventExtCmd 的类注释和实现都明确采用“整体覆盖、不解析不合并”，并直接执行 eventExt.setBizExtInfo(form.getBizExtInfo());。

    这与需求要求的“保留并合并多次更新图片”相反。

    后果
