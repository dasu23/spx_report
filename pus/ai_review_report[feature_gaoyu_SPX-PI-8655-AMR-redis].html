    问题

    RedisConfig.redisTemplate(@Qualifier("redissonClient") RedissonClient redissonClient) 新增了 @Primary 的自定义 StringRedisTemplate Bean。

    自定义 @Primary 基础设施 Bean 会让 Spring Boot / starter 对 RedisTemplate 相关自动装配让位，命中 AUTOCFG-001 规则；

    而本次 diff 中没有看到对自动装配原本提供的监控、连接工厂包装、统一配置兼容性进行等价校验。

    后果

    部署后其他模块若按类型注入 StringRedisTemplate 或依赖 starter 自动配置行为，会优先拿到这个手工创建的 Bean。

    若平台侧原本通过自动装配附加了连接池参数、监控埋点、序列化约定或其他包装能力，这些能力可能被静默绕过，导致线上 Redis 行为与既有环境不一致，严重时会引发缓存/会话/锁链路不可用或难以观测的问题。

    怎么改

    优先避免把手工创建的 StringRedisTemplate 标成 @Primary；

    如果必须保留双实例模板，建议仅通过明确的 @Qualifier("redisTemplate") / @Qualifier("redisTemplateLegacy") 注入使用，并确认平台自动装配能力是否需要显式复刻到自定义 Bean 上。

    至少补充一份兼容性说明或测试，验证现网依赖 StringRedisTemplate 的组件仍拿到预期 Bean。

    怎么验

    在 Spring 容器启动测试中同时注入 StringRedisTemplate（按类型）和带 @Qualifier("redisTemplate")、@Qualifier("redisTemplateLegacy") 的 Bean，验证默认注入对象是否符合预期；

    再覆盖一个依赖 Redis 自动装配的现有组件，确认引入 @Primary 后其序列化、连接和监控行为未发生变化。

    pus-infrastructure/src/main/java/io/speedx/pus/infrastructure/utils/RedisUtils.java1 Major1 个问题
    MAJORL115-116并发安全
    问题

    RedisUtils.incrementAndExpire(StringRedisTemplate template, String redisKey) 把 template.opsForValue().increment(redisKey, 1) 和 template.expire(redisKey, INCREMENT_EXPIRE_DAYS, TimeUnit.DAYS) 拆成了两条独立 Redis 命令执行，没有使用 Lua 脚本或单条原子命令保证二者同成败。

    这里命中了 REDIS-001 规则。

    后果

    当 increment 成功但 expire 因网络抖动、连接切换或 Redis 短暂异常失败时，increment_seq_no_ 下的计数器 key 会变成无 TTL 的永久 key。

    迁移方案依赖 90 天 TTL 来避免跨实例/跨日期复用，一旦部分 key 永久滞留在 redisTemplateLegacy 或 redisTemplate，后续 hasKey 路由会长期命中旧实例，导致计数器迁移行为偏离设计，增加持续写老实例和序列连续性异常的风险。

    怎么改

    把自增和设置过期时间改成单条原子操作，优先使用 Lua 脚本在 Redis 侧一次完成 INCR 与 EXPIRE；至少要保证只有在同一原子上下文里成功自增后才设置 TTL。示例：

    DefaultRedisScript<Long> script = new DefaultRedisScript<>();
script.setResultType(Long.class);
script.setScriptText("local v = redis.call('INCRBY', KEYS[1], ARGV[1]); redis.call('EXPIRE', KEYS[1], ARGV[2]); return v;");
Long value = template.execute(script, Collections.singletonList(redisKey), "1", String.valueOf(TimeUnit.DAYS.toSeconds(INCREMENT_EXPIRE_DAYS)));

    同时补充 expire 失败场景的集成测试，验证不会留下无 TTL 的计数器 key。

    怎么验

    模拟 template.opsForValue().increment(redisKey, 1) 成功、但 template.expire(redisKey, INCREMENT_EXPIRE_DAYS, TimeUnit.DAYS) 失败的场景；

    断言修复后不会出现“值已加 1 但 key 没有 TTL”的状态。若使用 Lua 脚本，再补一条测试验证脚本执行失败时计数器值不会被部分提交。
